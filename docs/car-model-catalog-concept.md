# Концепция: марка/модель авто (МП ↔ сервер ↔ 1С)

**Статус:** черновик для агента. Решение продукта/1С не выбрано.  
**Дата фиксации:** 2026-08-29.  
**Связано:** жалоба заказчика «машина не заполняется в заявке»; поля заявки `carMake` / `carModel`.

---

## 1. Проблема

- В **МП** пользователь вводит марку/модель **свободным текстом** (в лоб по наименованию).
- В **1С** это не строки, а **справочник моделей** с большим набором полей (утиль, таможня и др.). По одному названию с мобилки элемент справочника **полноценно не создать**.
- Сейчас в 1С: ищут по наименованию; **если нет точного совпадения — элемент не создают** → в заявке 1С марка/модель «пустые» / не сопоставлены, хотя на сервере текст с МП есть.
- Данные `carMake` / `carModel` на **сервере уже есть**; маппинг в справочник — зона **1С** (или будущий общий каталог на сервере).

---

## 2. Что обсуждают в 1С (ещё не выбрано)

С Олегом выбирают **один из двух** вариантов на стороне 1С:

| # | Вариант | Суть |
|---|---------|------|
| A | **Создавать «пустой» элемент** справочника по имени с мобилки | Менеджер потом дозаполняет обязательные поля справочника |
| B | **Не создавать** в справочнике | Писать присланное наименование в **отдельное текстовое поле** («не сопоставились, пользователь прислал: …») |

Пока: «возьмём один из двух, воткнём». Нашу сторону API заявки это может **не менять**, если остаются те же `carMake`/`carModel`.

---

## 3. Варианты «чтобы пользователь выбирал из справочника 1С»

Цель: снизить mismatch — в МП выбирать из того же каталога, что в 1С.

### 3.1. Онлайн-синк (как организации)

```
1С → API сервера (каталог / дельта) → БД сервера → API МП → UI выбора
```

- Плюсы: актуальные данные, тот же паттерн, что org sync.  
- Минусы: контракт с 1С, объём справочника, обновления, поиск на МП.

### 3.2. Файловый импорт

1С выгружает **Excel / CSV / XML / JSON** → импорт на сервер (админка или скрипт) → БД → МП.

- Плюсы: проще стартовать; не нужен постоянный HTTP-обмен на каждую модель; удобно отладить выгрузку.  
- Минусы: ручной/полуручной цикл; каталог устаревает до следующей выгрузки; нужен стабильный формат колонок с 1С.

**Практичный гибрид:** файл для первичного наполнения (+ периодических обновлений); позже при необходимости — API-дельты.

### 3.3. Оставить текст + маппинг только в 1С

Не тянуть справочник на сервер/МП. 1С выбирает A или B из §2.  
- Плюсы: минимум работ на нашей стороне.  
- Минусы: mismatch по названиям останется; жалобы «не заполнилось» возможны.

---

## 4. Архитектурные инварианты (не ломать)

- МП **не** ходит в 1С напрямую; всё через сервер.
- В заявке сейчас достаточно строк `carMake` / `carModel` (и при каталоге — скорее всего ещё `external1cId` / код элемента справочника — **решить при проектировании**).
- Полный «толстый» справочник 1С (все поля для утиля/таможни) на МП **не обязателен**: достаточно id + отображаемое имя (+ опционально марка→модели). Расчётные поля остаются в 1С.

---

## 5. Что нужно уточнить у 1С / продукта перед реализацией

1. Выбран ли вариант A или B (§2) — или вместо этого общий каталог на сервере (§3)?
2. Если каталог на сервере: **файл** или **API**? Частота обновления?
3. Объём: сколько записей? Иерархия марка → модель?
4. Что слать в create заявки: только текст, только id 1С, или оба?
5. Поведение, если в МП всё же разрешён свободный ввод «другая модель».

---

## 6. Когда вернёмся к задаче

1. Прочитать этот файл + `project-concept.mdc` (поля заявки).
2. Не изобретать маппинг заново: сервер уже хранит текст; дыра — справочник 1С / отсутствие каталога в МП.
3. План → утверждение пользователя → код (docs/server → app/admin по необходимости).
4. Не путать с VIN: VIN и марка/модель — разные поля; «только VIN в 1С» было симптомом отсутствия маппинга справочника, не отсутствия данных на сервере.

## 7. Не делать без явного ТЗ

- Не менять контракт create заявки «загодя».
- Не собирать APK из‑за этой темы.
- Не обещать 1С «мы уже импортируем справочник» — пока только концепция.
