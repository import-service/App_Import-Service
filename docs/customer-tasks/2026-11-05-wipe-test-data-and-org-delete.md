## Понимание

1. Удаление в 1С на сервер не доезжает — `POST /integration/organizations` умеет только upsert, endpoint'а «удалить орг» не было.
2. Нужна чистка: организации, созданные из 1С (GUID id_1c), кроме моков для тестового входа и служебных (declarant/svh).
3. Удаление должно быть штатно в **админке**, не разовым SQL.
4. Боевых данных нет — бэкап не требовался.

## Сделано

- `DELETE /api/admin/organizations/:id` — soft delete орги + каскад: заявки (`customs_requests` по `legal_email`), сессии (`user_sessions.revoked_at`), push-токены. Служебные роли (`svh_manager`, `declarant_manager`) endpoint не трогает — 404.
- Админка: кнопка «Удалить» в карточке организации (диалог деталей) с красным подтверждением.
- Зачистка прода (через новый endpoint): удалены 13 1С-организаций + 23 заявки каскадом + 1 сирота `polinka9730@gmail.com`.
- Осталось: 5 моков (`test_user`, `admin`, `admin@gmail.com`, `ip.test`, `curl-check`) + 6 служебных (5 declarant + 1 svh manager). Живых заявок: 0.

## Доп. итерация (тот же день)

- `POST /api/integration/organizations/delete {id_1c}` — 1С вызывает при удалении контрагента; каскад тот же (заявки/сессии/пуши). Идемпотентно (`alreadyDeleted`), 404 если не было, 403 на служебных. Логи — `integration_logs` с отдельным endpoint.
- `POST /api/admin/organizations/:id/restore` + `onlyDeleted` в списке + раздел «Удалённые» в админке с кнопкой «Восстановить» (орга + её заявки; сессии пересоздаются при входе).
- Общая логика удаления вынесена в `src/services/organizationCleanup.js` — админка и 1С зовут один код.
- Побочный бонус: повторный upsert с тем же `id_1c` сам воскрешает оргу (`deleted_at = NULL` уже был в `ON DUPLICATE KEY UPDATE`).
- Live-тест на проде: create → delete → alreadyDeleted → 404 → 403 staff → upsert-revive → admin restore — все ветки ок, тестовые строки убраны.
